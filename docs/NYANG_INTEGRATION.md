# Knowly 중심 냥대리 통합

`main`의 Knowly 인증·권한·검색·문서·FAQ·대화·평가 API를 유지하고 `nyang-fronted`와 후속 통합 브랜치의 냥대리 화면을 루트 앱으로 사용합니다. 기존 `feat/nyang-main-integration`의 화면 연결을 재사용하되 공용 직원/관리자 계정으로 대신 로그인하는 방식은 통합 앱에서 사용하지 않습니다.

## 기능 연결

| 화면 | 실제 연결 및 저장 |
| --- | --- |
| 직원·담당자 로그인 | 기존 Knowly Auth 개인 계정, `profiles.role` 확인 |
| 물어보기 | 기존 `chat` Edge Function, 연속 대화 ID, FAQ/RAG/LLM 결과와 출처·평가 |
| 사진·PDF·엑셀·텍스트 첨부 | main의 첨부 처리 코드, 최대 3개, 기존 개인정보 정책 유지 |
| 사내 문서·출처 | main의 문서 목록·원문 PDF/엑셀·청크 이동 |
| 미답변·통계·FAQ·문서·사용자·모델 설정 | main의 실제 관리자 화면을 같은 출처의 iframe에 표시 |
| 서버 대화 기록 | main의 대화 화면; 기존 대화와 새 질문은 Supabase에서 본인만 조회 |
| 대화 폴더·제목·저장 답변·내 일정 | 원래 냥대리 기능. 계정별로 **서버(`nyang` 함수)에 저장**해 어느 PC에서나 보임 (화면은 브라우저 저장소를 쓰고 뒤에서 서버와 맞춤) |
| 질문 게시판·답변·삭제/복원·좋아요 | **서버(Supabase `nyang` 스키마)에 저장**. 모든 직원·담당자가 공유 |
| 출석·질문 경험치·포인트·츄르·하트·꾸미기·쓰다듬기 | 기존 냥대리 보상 규칙, 계정별로 **서버에 저장** |
| 고양이 성격·표정·배경·다크 모드·움직임 설정 | 원래 냥대리 화면/상호작용 유지. 성격·고른 배경·움직임은 서버와 맞추고, 직접 올린 배경 이미지와 다크 모드는 기기마다 따로 둠 |

질문 예시 버튼도 실제 Knowly에 질문합니다. 검색 실패나 근거 부족을 샘플 FAQ 답변으로 바꾸지 않습니다. 분야 선택은 화면 분류이며 Knowly 검색은 기존처럼 등록된 전체 문서/FAQ를 대상으로 합니다. 일정은 브라우저 계획 도구이며 기존 샘플 일정 규칙을 사용하므로 회사 규정의 자동 승인이나 외부 캘린더 연동이 아닙니다.

## 실행·배포

저장소 **루트**에서 실행합니다. `nyang-frontend/`는 원본 UI와 이전 독립 프로토타입의 보존본이며, 그 디렉터리의 Worker/D1 배포는 통합 앱 배포 경로가 아닙니다.

```sh
npm ci
# .env.example → .env.local: 기존 VITE_SUPABASE_URL / VITE_SUPABASE_PUBLISHABLE_KEY
npm test
npm run dev
npm run build
```

`prepare:nyang`가 원본 UI 자산을 `public/nyang/`에 준비하고, `build:nyang-embed`가 main의 화면·첨부 모듈을 `public/knowly/`에 빌드합니다. 생성물은 커밋하지 않습니다. 최종 `dist/`는 기존 Vercel 정적 배포 대상입니다. `/docs/*`, `/admin/*` 링크도 Knowly 화면으로 이어집니다.

### 서버 저장 (2026-11-17)

2026-11-14에는 운영 DB를 바꾸지 않으려고 냥대리 기록을 **브라우저에만** 저장했습니다. 그래서 다른 PC로 로그인하면
기록이 보이지 않았고, 2026-11-17에 다시 **서버 저장**으로 바꿨습니다.

- DB: `supabase/migrations/20261117000000_nyang.sql`이 운영 Supabase에 `nyang` 스키마(표 10개)를 더합니다.
  기존 Knowly 표·권한은 바꾸지 않습니다. `anon`·`authenticated`는 접근할 수 없고(권한 회수 + 행 보안), 서버 함수만 씁니다.
- 서버 함수: `supabase/functions/nyang`. 로그인 토큰으로 Knowly 프로필을 확인해 계정·역할을 정하고(요청 본문의 역할은 믿지 않음),
  요청 하나를 Postgres 트랜잭션 하나로 처리합니다. 규칙은 브라우저 저장소와 **같은 코드**(`nyang-frontend/lib/*.mjs`)를
  `_shared/nyang`에 복사해 씁니다. 원본을 고치면 `npm run sync:nyang-server`를 실행하세요(다르면 `npm test`가 실패합니다).
- 개인 기록(내 일정·대화 기록·내 활동 기록·읽은 답변·성격·고른 배경·움직임): `nyang.user_state`에 계정별로 저장합니다.
  화면은 전처럼 브라우저 저장소를 쓰고, `nyang-frontend/public/account-sync.js`가 로그인 때 서버 기록을 받아 오고
  저장할 때마다 잠시 뒤 서버로 보냅니다. 연결이 끊기면 표시해 두고 다음에 다시 보냅니다. 기록 하나가 1MB를 넘으면 그 기록은 브라우저에만 둡니다.
- 기존 기록 옮기기: 브라우저에만 있던 기록은 그 브라우저에서 처음 로그인할 때 서버로 한 번 올립니다(`src/nyang/local-export.mjs`).
  올리는 사람 **자신이 한 일**만 받고(uid는 로그인 계정으로 정함), 지갑은 브라우저마다 한 번만 옮깁니다.
  글쓴이가 아직 올리지 않아 미뤄진 유익해요·답변은 다음 로그인 때 다시 올립니다. 브라우저의 원래 기록은 지우지 않습니다.
- 직접 올린 배경 이미지(`om-bg-uploads-*`), 추가 자료(`om-docs`), 다크 모드는 용량·기기 특성 때문에 계속 브라우저에만 둡니다.

## 검증 및 운영 확인

자동 검증: `nyang` 마이그레이션을 실제 Postgres(PGlite)에 적용해 보상·게시판·권한·통계·개인 기록·기존 기록 옮기기를 확인하는 테스트(`tests/nyang-server.test.mjs`), main 검색 테스트, 개인 로그인/역할 확인·첨부·연속 대화·평가 전송 테스트, 냥대리 회귀 테스트, 브라우저 저장소(sql.js)에서 같은 시나리오로 보상·중복 요청·계정 격리·게시판 권한·실패 시 저장 안 함 테스트(`tests/nyang-local.test.mjs`).

브라우저 확인은 로컬 서버 접근 시간 초과 및 Windows 컴퓨터 사용 도구의 URL 판별 실패로 완료하지 못했습니다. 실제 Supabase 로그인·LLM·원문 파일 요청도 운영 자격 증명 없이 검증하지 않았습니다. 배포 후 아래를 확인하세요.

1. 서로 다른 직원 계정으로 로그인해 대화/보상이 분리되는지 확인합니다.
2. 질문 예시·자유 질문·근거 없는 질문·첨부 질문을 보내고, 실패 시 샘플 답변으로 바뀌지 않는지 확인합니다.
3. 출처 원문, 피드백, 서버 대화 기록, 새 대화와 이어 질문을 확인합니다.
4. 일정·폴더·출석·쓰다듬기·츄르·꾸미기·게시판과 담당자 답변/복원을 확인합니다.
5. 담당자 계정으로 기존 6개 관리자 화면을 확인하고 직원 계정의 관리자 접근이 차단되는지 확인합니다.
